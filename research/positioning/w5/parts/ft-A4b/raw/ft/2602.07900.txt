 Abstract 
 Large Language Model (LLM) code agents increasingly resolve repository-level issues by iteratively editing code, invoking tools, and validating candidate patches. In these workflows, agents often write tests on the fly, but the value of this behavior remains unclear. This raises a central question: how does agent-written testing relate to task outcomes and resource use during repository-level issue resolution? 
 To better understand the role of agent-written tests, we analyze 5,000 recorded agent runs produced by six strong LLMs on SWE-bench Verified using the lightweight mini-SWE-agent scaffold.
Our results show that test writing is common for most models. GPT-5.2 is an exception: it rarely writes new test files while achieving a resolution rate close to the top-ranked model. Test-writing frequency varies widely across models. Within a given model, it differs less between resolved and unresolved tasks. When tests are written, their files contain substantially more statements that print runtime values than assertions that check conditions. We then compare baseline prompts with revised prompts that encourage or discourage writing new test files for four models. Agents start or stop writing test files as requested on 36.8%–93.2% of tasks. Resolved-task totals differ by 0–13 out of 500 per model, with no statistically significant difference, while API calls or token use differ substantially for three models. Similar resolution totals can therefore hide substantial differences in how agents test and how many resources they use.

Large Language Models, Code Agents, Software Testing, Repository-Level Issue Resolution, SWE-bench
 I Introduction 
 Code agents combine Large Language Models (LLMs)  [ 1 , 2 ] with tools to inspect repositories, edit code, and resolve software issues  [ 3 , 4 , 5 , 6 , 7 ] . We use code agent to denote an LLM operating in an iterative action–observation loop, and scaffold to denote the interface and protocol that govern its tools and feedback. Testing supports this workflow by exposing regressions and checking hypotheses during patch development  [ 8 , 7 , 9 , 10 ] . 
 Repository-level agents can validate patches with existing human-written tests, which reflect project conventions and developer intent  [ 11 , 12 ] , or with agent-written tests created during issue resolution. Agent-written tests can surface edge cases and support fault localization, but incorrect expectations about program behavior can redirect the repair process. Writing and running them also consumes API calls, tokens, and context  [ 13 ] .
These temporary tests give agents a way to inspect program behavior through execution and printed values, connecting testing with program comprehension. Resolution rate alone does not capture this activity or its resource use. 
 To better understand agent-written tests, we conduct a quantitative analysis of agent trajectories on SWE-bench Verified  [ 14 ] using mini-SWE-agent   [ 15 ] . Its default prompt recommends testing edge cases and leaves whether, when, and how to test to the model. Agent-written testing is prevalent for several strong models in this setup.
For example, Claude Opus 4.5 (ranked #1 in this setting, 74.4% resolution) writes a detected test file in 83.6% of tasks.
By contrast, GPT-5.2 achieves a comparable resolution rate (71.8%), only 2.6 percentage points below Claude Opus 4.5 , while writing detected test files in only 2.4% of tasks.
This observation motivates a core question: how does agent-written testing relate to task outcomes and resource use during repository-level issue resolution? 
Answering this question requires a systematic empirical study of testing behavior, test-file content, and differences across test-writing prompt conditions. 
 Prior work mostly evaluates LLM-generated unit tests, assertions, or issue-reproducing tests against a fixed target program or code snapshot  [ 16 , 17 , 18 , 19 , 20 , 21 , 22 ] . However, in complex real-world GitHub issue resolution  [ 11 , 23 ] , the codebase and candidate patches evolve over time, and testing occurs within the broader repair process rather than as a standalone evaluation objective. Existing studies commonly focus on either generated test artifacts or agent trajectories. We connect these perspectives by examining how strong models write and execute tests within repository-level repair under a lightweight scaffold and how outcomes and resource use differ across test-writing prompts. 
 Research questions and overview 
 We organize the study around three research questions.
 RQ1 characterizes the agents’ testing behaviors under a lightweight scaffold where test writing is optional: whether agents write tests, when they introduce them, and how intensively they execute them.
 RQ2 shifts from behaviors to test content , investigating how many assertions and value-revealing prints appear in agent-written test files, what forms the assertions take, and what kinds of runtime information the prints expose.
 RQ3 compares paired prompt conditions that encourage or discourage writing new test files, measuring differences in test-writing behavior, task resolution, API calls, and tokens. 
 The contributions of this work can be summarized as follows: 
 • 
 A cross-model analysis of agent-written testing behavior. 
Across 3,000 baseline trajectories, we characterize whether, when, and how six LLMs create and execute test files, finding wide behavioral variation that does not follow the ranking of resolution rates. 
 • 
 An analysis of assertions and value-revealing prints in agent-written test files. 
Rule-based analyses of Python abstract syntax trees (ASTs) characterize the conditions that assertions check and the runtime information that prints expose. Across the five analyzed models, statements that display runtime values outnumber assertions. 
 • 
 A comparison of task outcomes and resource use across test-writing prompts. 
Across 2,000 task-level pairs, agents start or stop writing test files as requested on 36.8%–93.2% of tasks; none of the four model-level outcome differences is statistically significant, while resource use differs substantially for three models.

 II-A Benchmark 
 We use SWE-bench Verified as our benchmark. The original SWE-bench benchmark is built from resolved GitHub issues drawn from 12 open-source Python repositories  [ 11 ] . SWE-bench Verified is a 500-instance subset released after a human-screening effort led by OpenAI in collaboration with the SWE-bench authors  [ 14 ] . Each instance provides a GitHub issue, a fixed repository snapshot, and an evaluation harness that checks whether a patch passes the issue-specific and regression tests. We use this official harness outcome to label each task as resolved or unresolved. 
 II-B Agent Scaffold and Models 
 Many recent LLM-based agents incorporate dedicated testing components, such as specialized validation modules, test-planning stages, or multi-agent coordination  [ 9 , 8 , 24 ] .
We adopt mini-SWE-agent   [ 15 ] as a lightweight scaffold in which testing choices remain model-controlled.
The agent interacts with the repository through a single bash tool, using shell commands to inspect and modify files and run programs such as Python.
The model can create executable Python test files on the fly and run them via bash as part of its workflow.
The default mini-SWE-agent prompt includes a brief natural-language recommendation: “Test edge cases to ensure your fix is robust.”
Beyond this brief cue, the model controls whether, when, and how to test through the standard bash interface.
Our measurements characterize how each model tests in this prompt-and-scaffold setup.

 II-C Data Extraction of Agent-Written Tests 
 We extract agent-written test files from trajectories: time-ordered logs of the agent’s reasoning, bash actions, and environment observations. We call each detected Python test file a test artifact . We retain actions with logged environment return codes, excluding rejected action formats. A shared deterministic pipeline detects commands that write complete files through heredocs, echo / printf redirection, and Python writes whose paths and contents can be recovered without executing the command. It keeps Python filenames starting with test or ending with _test.py or tests.py , extending common test-discovery conventions  [ 29 ] . Paths are normalized relative to /testbed and counted once per task. Later whole-file writes update the stored content; RQ2 analyzes the last detected version of each file. Files in temporary directories are distinguished by the action and source line that create the directory. 
 An execution event is a logged bash action that invokes a recognized Python or test runner with a detected file as an argument. Each action counts once, including actions containing multiple commands, and receives its logged return code. This definition measures execution actions rather than individual test cases. 
 II-D Implementation Details 
 We run the 2,000 revised-prompt trajectories with mini-SWE-agent 1.17.2 on Ubuntu 22.04.5 and evaluate their patches with the official SWE-bench sb-cli . The corresponding public baselines use release 1.15.0 for Gemini, 1.17.1 for Kimi and DeepSeek, and 1.17.2 for GPT-5.2. Revised GPT and Gemini runs use OpenRouter; Kimi and DeepSeek use their provider APIs. The released trajectory metadata records the exact model identifiers, decoding settings, prompts, and run limits for both conditions. The revised runs cost approximately USD 1,600 in total. 
 III RQ1: What Testing Behaviors Emerge Under a Lightweight Agent Scaffold? 
 Motivation 
 RQ1 establishes a descriptive baseline of whether agents write tests, when they introduce them, and how intensively they run them when testing is optional. 
 Experiment Design 
 We compare resolved and unresolved trajectories descriptively across test-writing frequency, timing, and execution; these comparisons do not estimate a causal effect of testing on success.
We use two-sided Mann–Whitney U tests for comparisons within each model. For comparisons combining all models (pooled), task-clustered permutation tests keep the six models’ outcomes for the same task together. Holm correction is applied within each table.
Pooled means give each eligible task–model run equal weight.

 RQ1.1 Test Writing: Key Finding 
 Writing new test files more often does not necessarily mean solving more issues. On the same 500 issues, GPT-5.2 creates new test files in 2.4% of its attempts and solves 71.8% of the issues. Kimi K2 Thinking creates new test files in 97.6% of its attempts but solves 63.4% of the issues.

 Table  II shows that the mean last writing position lies late in the trajectory (0.67–0.86). Gemini 3 Pro starts later and has the shortest span (0.13–0.14), while MiniMax M2 has the widest span (0.51–0.57). 
 RQ1.2 Writing Timing: Key Finding 
 On unsolved issues, test-file writing extends over a larger portion of the repair process. For attempts with test files, we measure the steps from the first test-file write to the last as a share of all interaction steps. Combining the six models, this share averages 43% for unsolved issues and 38% for solved issues. 
 III-C RQ1.3 Execution: How Intensively Are Agent-Written Tests Executed, and With What Action Outcomes? 
 Goal and measurements 
 RQ1.3 describes how agents execute tests after they have written them.
We measure (i) the number of test-execution actions, (ii) execution actions per written artifact, and (iii) the fraction of these actions with a non-zero exit code.
An action can fail because of a test, an environment error, or another command in the same action; its return code does not isolate assertion failures. 
 For each task t t , let E t E_{t} be the number of test-execution actions, A t A_{t} the number of agent-written test artifacts, and Z t Z_{t} the number of these actions with non-zero return codes.
We report three task-level metrics:
 execution actions per task ( E t E_{t} );
 execution actions per test file ( E t / A t E_{t}/A_{t} );
and nonzero-exit rate ( Z t / E t Z_{t}/E_{t} ), the fraction of executions with a non-zero return code.
We compute each metric per task and then average the resulting values. The first two metrics use all tasks with test artifacts; the nonzero-exit rate uses tasks with E t > 0 E_{t}>0 , because the ratio is undefined when no test execution is detected.

 Agents run newly written tests more often on issues they fail to solve. Among attempts that create test files, we count tool calls that run these files. Combining the six models, the average is 6.45 such calls per unsolved issue and 4.82 per solved issue. 
 IV RQ2: What Assertion and Value-Revealing Print Patterns Appear in Agent-Written Tests? 
 Motivation 
 Agent-written test files can encode both explicit checks and statements that expose runtime information.
RQ1 treats tests as events in the trajectory, measuring whether agents write them, when they appear, and how often they are run.
RQ2 shifts to the content of those files and characterizes two common statement types:
 assertions , which specify conditions to check, and value-revealing prints , which expose runtime values or execution information. 
 Experiment Design 
 RQ2 examines tasks in which the agent writes at least one test file and summarizes three aspects of file content: 
 • 
 Statement counts (RQ2.1): assertion vs. value-revealing print counts in agent-written tests. 
 • 
 Assertion types (RQ2.2): what types of assertions appear in agent-written tests, using a four-type categorization. 
 • 
 Print types (RQ2.3): what runtime information value-revealing prints expose, using a three-type categorization. 
 RQ2.1 stays at the task level and measures aggregate assertion and print counts. RQ2.2 and RQ2.3 then move to the statement level , categorizing assertion and value-revealing print statements separately. 
 IV-A RQ2.1 Task-level statement counts: What statements do agent-written tests contain? 
 Goal and measurements 
 For tasks with at least one agent-written test file, we count the assertions and value-revealing prints in those files.
We distinguish two statement types: (i) assertions ( A A ), i.e., native assert statements and recognized framework assertion calls that specify explicit checks, and
(ii) value-revealing prints ( P P ), i.e., print statements with at least one argument that depends on a variable, attribute, indexed value, runtime expression, or function call. We exclude prints composed only of literals, including fixed messages and expected-value text (e.g., print("Expected: 3") and print("=" * 60) ), while retaining statements such as print(obj.attr) .
Because GPT-5.2 produces test artifacts in only 12 of 500 baseline tasks, we exclude it from the cross-model content summaries in RQ2. The same AST rule is used for the task-level counts in RQ2.1 and the print categories in RQ2.3. Of the 8,041 artifacts from the five models analyzed in RQ2, 8,028 parse successfully; the remaining 13 contribute no assertion or print statements to these analyses.

 RQ2.1 Statement Counts: Key Finding 
 Agent-written test files contain more statements that show runtime information than statements that check conditions automatically. For example, print(result) shows a value; assert result == expected checks it. After totaling these statements across the test files for each issue, the average print count exceeds the average assertion count for all five models, on both solved and unsolved issues. 
 IV-B RQ2.2 Assertion categorization: What kinds of verification do assertions encode? 
 Goal and measurements 
 RQ2.1 counts assertion statements in agent-written tests, but counts alone do not tell us what those assertions check.
Assertions can enforce basic preconditions (e.g., non- None or type checks) or compare results with expected values or structures.
Models may therefore differ not only in how often they assert, but also in what forms of checks they write. RQ2.2 provides a descriptive breakdown of assert statements into four assertion categories: 
 • 
 C1 Sanity checks. 
The assertion checks truthiness, identity, existence, or type.
 Example: assert x is not None . 
 • 
 C2 Property checks. 
The assertion checks a property of a value or object (e.g., membership or validity) without fixing an exact output.
 Example: assert key in mapping . 
 • 
 C3 Relational checks. 
The assertion enforces a range, bound, inequality, or approximate relationship between values. Example: assert 0 <= score <= 1 .
This category also includes checks that expect a specific exception, because they constrain the allowed behavior to “must fail with an exception of type E E ” rather than matching a single concrete output. 
 • 
 C4 Exact checks. 
The assertion checks equality with an expected value or structure, whether represented by a literal or a variable.
 Example: assert output == expected_output . 
 To identify and categorize assertions, we implement a rule-based classifier over Python ASTs and map each assertion to exactly one category.
The classifier covers both native assert statements (e.g., assert a == b ) and framework-provided assertion calls (e.g., self.assertEqual(a, b) in unittest ). Concretely, for each test artifact, we parse the code into an AST and extract:
(i) native assert <expr> statements, and
(ii) calls to framework assertion APIs. Some assert statements contain multiple checks joined by Boolean operators (e.g., assert a > 0 and b == 1 ). For these compound statements, we recursively split the expression into atomic checks and assign the highest-numbered category present. This keeps one observation per source statement; the category numbers define the tie-breaking rule, not an empirical ranking of assertion quality. Thus, the example receives C4 because a > 0 is C3 and b == 1 is C4. 
 We check three alternative ways to classify compound assertions: choosing the lowest-numbered category, using the first check’s category, or counting each check separately. Compound Boolean expressions occur in 161 of 8,139 native assert statements (2.0%; 1.8% of all 8,796 assertions). Across the three alternatives, C4 remains the largest category (56.96–57.09%) and C3 the smallest (5.09–5.17%).

 IV-C RQ2.3 Print categorization: What information do value-revealing prints expose? 
 Goal and measurements 
 Since value-revealing prints substantially outnumber assertions, RQ2.3 categorizes the information exposed by these statements as concrete values or content, structural summaries, or exception and execution-status information: 
 • 
 P1 Value / content inspection. 
The print exposes a concrete runtime value or content, such as a returned output, an intermediate result, an object field, or part of a generated string. This category captures what the program produced , rather than a structural summary or an error/status signal;
 e.g., print(add(1, 2)) . 
 • 
 P2 Structural summary inspection. 
The print reports an aggregate structural summary, such as length, size, shape, number of items, or emptiness. This category is reserved for prints that summarize how much data is present or what structure it has, rather than showing the content itself;
 e.g., print(len(items)) . 
 • 
 P3 Exception / execution-status signals. 
The print surfaces an exception, an error message, or a coarse execution-status indicator, such as a success/failure flag. This category is used when the print primarily indicates what happened during execution , rather than the program’s computed content;
 e.g., except Exception as exc: print(exc) . 
 We implement a rule-based classifier over Python ASTs. Using the same inclusion rule as RQ2.1, we extract value-revealing print(...) calls and apply the categories in a fixed order: P3 for prints in exception handlers or with exception/status cues, P2 for size-, shape-, or count-oriented expressions, and P1 for the remaining included prints.  V RQ3: How Do Outcomes and Resource Use Differ Across Test-Writing Prompt Conditions? 
 Motivation 
 RQ1 shows that models with similar issue-resolution rates can differ sharply in how often they write test files. RQ2 shows that these files contain more value-revealing prints than assertions. RQ3 examines outcomes and resource use under prompts that encourage or discourage new test files. 
 Experiment Design 
 RQ3 compares task-resolution outcomes (RQ3.1) and resource use (RQ3.2) between baseline and revised prompt conditions. 
 Model selection 
 We select models by their baseline test-writing rates (Table  I ). The encourage-test comparison uses GPT-5.2 (2.4%) and Gemini 3 Pro (62.0%), whose baselines leave room for more test creation. For the discourage-test comparison, the experiment budget supported two models; we selected Kimi K2 Thinking (97.6%) and DeepSeek v3.2 Reasoner (88.4%) from the high test-writing group. 
 We use the mini-SWE-agent prompt to create two variants: 
 • 
 Encourage writing tests: for GPT-5.2 and Gemini 3 Pro , we append prompt instructions to write at least one runnable new test file (a file whose name starts with test_ or ends with _test.py ), separate from the repository’s existing tests. 
 • 
 Discourage writing tests: for Kimi K2 Thinking and DeepSeek v3.2 Reasoner , we remove the default testing-related prompt cue from mini-SWE-agent and append prompt instructions not to write any new test files or scripts. 
 Reference prompt templates are included in experiment_prompts ; each trajectory records its exact prompt. Gemini’s encouragement prompt repeats the instruction in action feedback, whereas GPT-5.2’s uses system and instance instructions. We compare each revised condition with its public baseline on the same tasks.

 VI Discussion and Future Work 
 VI-A Implications 
 Identical resolution totals can hide changes in which issues an agent solves. GPT-5.2 resolves 359 issues under both prompts, but 27 change from failure to success and another 27 change in the opposite direction (Table  VII ). The encouragement condition also uses more tokens. Comparing individual task outcomes and resource use therefore reveals differences that the overall resolution rate misses. 
 Test-file creation records a workflow choice; resolution measures whether the final patch passes the benchmark’s tests. Their different rankings across models make both measurements useful when comparing agents. Reporting whether instructions encourage, discourage, or leave new-test creation to the model also helps explain the setting in which these choices occur. 
 Agent-written test files combine automatic checks with code for inspecting program behavior. Across the five models in RQ2, value-revealing prints outnumber assertions, and most display concrete values such as returned results or object fields. Assertions encode conditions to check; prints expose information that an agent can inspect. Evaluations should distinguish these two forms of test content. 
 VI-B Future work 
 A next question is which test outputs lead agents to change their diagnosis or next edit. Trajectory-level analyses can trace these links for new tests, repository tests, and inline commands. Test-quality analyses can also account for transient repository states, where intermediate code and tests may later be overwritten, and examine whether agent-written tests remain useful with the final patch  [ 30 , 31 , 32 , 33 , 34 , 35 , 36 ] . 
 VI-C Threats to Validity 
 Internal validity. 
Each prompt condition is observed once per task. Pairing controls task identity, but scaffold releases and API routes differ between some public baselines and revised runs. Decoding and environment variation may also affect outcomes. We therefore interpret the comparisons as observed differences between conditions, without attributing them solely to the prompt edits. 
 External validity. 
Our results cover six LLMs on Python issues from SWE-bench Verified under one lightweight scaffold. Testing conventions, repository languages, and scaffolds with dedicated validation tools may produce different behavior. 
 Data construction validity. 
Our measures cover detected whole-file writes and execution actions; inline-only checks, unmodified repository tests, and indirect file operations fall outside this scope. Local edits may change a file after its last recovered snapshot. Execution return codes describe entire bash actions. AST categories characterize syntax, which may not fully capture semantic intent; static counts do not establish that statements execute or guide later edits. The extraction rules and regression checks are released with the data. 
 VII Related Work 
 LLM-Generated Tests 
 Research on LLM-based software testing commonly treats the test artifact as the primary output. Empirical studies evaluate generated unit tests and test suites, while assertion-generation work examines the checks of expected behavior within those tests  [ 22 , 19 , 17 ] . Broader evaluations and surveys organize this literature across software-testing tasks and requirements-based test generation  [ 37 , 38 ] . Benchmarks make these targets explicit: TestEval benchmarks test-case generation, and SWT-bench evaluates tests for validating real-world bug fixes  [ 20 , 18 ] . These settings provide controlled tasks for assessing generated artifacts. We examine a different unit of analysis: the test-writing process within a multi-step repair trajectory. This process view captures whether an agent creates a new test, when it does so, whether it executes the file, and what assertion and printed-value patterns the file contains. 
 Testing During Repository-Level Issue Resolution 
 SWE-bench established real-world GitHub issue resolution as an evaluation setting for language models  [ 11 ] . Systems such as SWE-agent and AutoCodeRover study how models interact with repository environments and tools to carry out software-engineering tasks  [ 3 , 8 ] . Recent systems span repository repair tools, autonomous coding agents, test-time-scaled repair, and role-based multi-agent development workflows  [ 39 , 40 , 41 , 42 ] . Within these end-to-end workflows, testing is one activity among repository exploration, code editing, command execution, and patch validation. A final resolution score therefore does not show whether an agent wrote new tests or what resources accompanied that behavior. We study six LLMs under one lightweight, bash-only scaffold whose default prompt provides an advisory testing cue while leaving concrete testing decisions to the model. We then compare testing behavior, resolution outcomes, and resource use between baseline prompts and prompts that encourage or discourage new-test writing. 
 Software-Agent Trajectories 
 Process-oriented studies complement final patch scores by examining the steps agents take during issue resolution. Bouzenia and Pradel analyze thought–action–result trajectories; Majgaonkar et al. compare successful and failed trajectories across code agents; Ceka et al. trace APR-agent workflows and identify test generation and regression-test selection as bottlenecks; and Chen et al. study errors across the software-development process rather than only the final code  [ 43 , 44 , 45 , 46 ] . Systematic failure analysis also identifies diagnostic errors and unproductive loops in automated issue solving  [ 47 ] . Building on these process studies, including their attention to testing bottlenecks, we provide a cross-model account of file creation, timing, and execution under a lightweight scaffold. We further characterize assertion/print composition and compare paired prompt conditions in terms of both task outcomes and resource use. 
 VIII Conclusion 
 This paper studies how LLM agents write and execute tests during GitHub issue resolution, using 5,000 recorded runs from six LLMs under a lightweight scaffold. Models differ substantially in whether, when, and how they test. For every model in the content analysis, statements that print runtime values outnumber assertions that check conditions. Under prompts that encourage or discourage new test files, agents often start or stop writing them. None of the resolution differences from the original prompts is statistically significant, while API calls or token use differ substantially for three models. These test files combine automatic checks with code that exposes runtime values for inspection, connecting agent-written testing with program comprehension during repair. Identical resolution totals can also hide changes in which issues are solved, as the GPT-5.2 comparison shows. Evaluations should therefore report testing instructions, assertion and print content, test execution, task-level outcomes, and resource use alongside resolution rates.
