Abstract.
Existing evaluation protocols for LLM-generated unit tests rely on aggregate metrics such as branch coverage and mutation score. These metrics quantify the extent to which a test suite exercises program behavior, but do not identify the behavioral obligations it systematically leaves unchecked.
We propose
BlindSpotEval
, an obligation-based evaluation framework aligned with the Arrange-Act-Assert pattern. The framework comprises three metrics, Boundary-Value Adequacy, Control-Flow Adequacy, and Oracle Strength, complemented by an assessment of execution reliability. We also introduce
ObligBench
, a complexity-stratified Java benchmark comprising 895 complex and 700 low-complexity functions with source-side obligation annotations.
Applied to 14,320 tests generated by four LLMs under four prompting strategies,
BlindSpotEval
reveals systematic blind spots that aggregate metrics do not distinguish. Before adequacy scoring, 19.7% of tests fail to execute successfully, with failures ranging from compilation errors to runtime exceptions.
Among test failures, 15.6% involve incorrect assertions, termed wrong-oracle failures. Such tests can contribute to code coverage despite failing, illustrating that coverage alone does not establish oracle correctness.
Among executable tests, LLMs readily cover directly inferable boundary cases but struggle with non-inferable ones. Coverage of
null
,
negative
, and
empty
arguments reaches only 34.8%, 23.8%, and 38.8%, compared with average coverage above 93% for booleans.
Exceptional control flow exhibits a similar pattern.Exceptional and fallback behavior is weakly checked, with CFA scores of 0.100 for catch blocks and 0.312 for default groups.
Across both dimensions, LLM-generated tests exhibit the
happy-path
bias observed in human-written tests, concentrating on normal inputs and expected flows while leaving unusual values and exceptional paths unchecked.
Oracle strength is high on average but uneven, with weaker assertions for object return property values and exceptions.
These blind spots also occur in low-complexity functions, suggesting that code complexity alone does not explain them.
BlindSpotEval
provides construct-level adequacy profiles that identify under-tested obligation types and can guide targeted improvements beyond those supported by aggregate scores alone.
1.
Introduction
Software testing is fundamental to software quality, it provides a primary mechanism for developers to assess whether code behaves as intended and whether changes introduce regressions
(
Ammann and Offutt, 2016
;
Myers et al., 2011
)
. As large language models (LLMs) increasingly support code generation and modification
(
Chen et al., 2021
)
, automated unit test generation has become correspondingly important. Research on LLM-based test generation has advanced rapidly, producing a range of approaches. Zero-shot prompting generates tests directly from the function signature and body
(
Chen et al., 2024
;
Schäfer et al., 2024
;
Siddiq et al., 2024
;
Tang et al., 2024
;
Yang et al., 2024
)
, feedback-based approaches iteratively refine tests using coverage or mutation signals
(
CodiumAI, 2024
;
Dakhel et al., 2024
;
Yuan et al., 2024
)
, and planning-based approaches first reason about the function’s intent
(
Gu et al., 2026
)
. Recent tools regularly produce tests that compile, run, and achieve high branch coverage and competitive mutation scores
(
Jain et al., 2025
;
Chen et al., 2024
)
.
High aggregate scores, however, do not necessarily indicate thorough testing. Prior work commonly evaluates LLM-generated tests using branch coverage, which measures the proportion of program branches executed
(
Zhu et al., 1997
;
Fraser and Arcuri, 2011
)
, and mutation score, which measures the proportion of artificially injected faults detected
(
Jia and Harman, 2011
;
Coles et al., 2016
)
. A replicability study found that these metrics correlate with fault detection only under restricted conditions
(
Zhao et al., 2026
)
. Although useful for summarizing test effectiveness, these metrics do not directly identify which obligations remain unchecked. For example, tests using only ordinary inputs may achieve the same line coverage as tests that also check boundary values whenever those inputs traverse the same statements. Similarly, a high mutation score indicates sensitivity to injected changes without necessarily establishing whether tests adequately check particular input boundaries, exceptional paths, or behavioral properties. These distinctions have practical consequences. Omitting
null
inputs may leave null-handling faults undetected, failing to exercise exception handlers may leave exception-swallowing behavior unchecked, and weak assertions may allow incorrect results to pass unnoticed.
Scores of 90% mutation adequacy and 80% branch coverage alone do not establish whether null inputs, exception paths, or object-state invariants have been adequately tested.
Unit tests are commonly structured according to the Arrange-Act-Assert (AAA) pattern
(
Osherove, 2014
;
Meszaros, 2007
)
. The
Arrange
phase prepares the inputs, the
Act
phase invokes the function, and the
Assert
phase verifies the resulting behavior. This structure suggests three complementary evaluation dimensions, (1) tests should cover relevant input boundary values during Arrange; (2) tests should exercise relevant control-flow alternatives during Act; and (3) tests should verify the resulting behavior through their assertions. We refer to the behaviors that tests should exercise or verify, as identified from a function’s implementation, as
obligations
. Our aim is to identify systematic blind spots in how LLM-generated tests satisfy these obligations.
Existing approaches primarily assess generated tests through aggregate metrics. CoverAgent
(
CodiumAI, 2024
)
seeks to maximize branch coverage but provides no construct-level diagnosis of what remains unchecked; MuTAP
(
Dakhel et al., 2024
)
and ChatTester
(
Yuan et al., 2024
)
use mutation feedback to improve tests, with aggregate mutation scores serving as an evaluation measure. To the best of our knowledge, no existing framework jointly assesses LLM-generated tests at the obligation level across all three AAA dimensions.
We propose
BlindSpotEval
, an obligation-based evaluation framework aligned with the AAA pattern
(
Osherove, 2014
;
Meszaros, 2007
)
. For each function under test, the framework assesses which input boundaries, control-flow alternatives, and behavioral properties the generated tests exercise or verify.
Before assessing adequacy, we examine execution reliability through the following research question:
RQ1 (Executability).
To what extent do LLMs generate compilable and runnable tests, and what are the common failure modes?
We measure execution success across multiple LLMs and prompting strategies and characterize failure modes to distinguish execution failures from adequacy gaps.
For tests that compile and execute successfully, we then investigate three dimensions of adequacy.
RQ2 (Arrange).
To what extent do LLM-generated tests cover the input boundary values relevant to a function?
We propose
Boundary-Value Adequacy
(BVA), which statically extracts per-parameter obligations and assesses whether the generated tests cover them.
RQ3 (Act).
To what extent do LLM-generated tests adequately exercise the control-flow alternatives within a function?
We propose
Control-Flow Adequacy
(CFA), which uses extreme-condition mutation to assess obligations associated with conditions, exception handlers, and switch cases.
RQ4 (Assert).
To what extent do LLM-generated tests verify a function’s outputs and exception behavior?
We propose
Oracle Strength
(OS), which mutates return values and exception behavior and assesses whether the tests’ assertions detect these changes. We exclude incidental kills caused by unexpected exceptions or crashes from the killed-mutant count, so that these failures do not inflate the estimated strength of the test oracles.
Finally, we examine whether the observed blind spots also occur in less complex code:
RQ5 (Complexity).
To what extent do the observed blind spots persist across levels of code complexity?
We compare complex functions with a low-complexity control set to assess whether the identified gaps are concentrated in complex code or also occur in simpler functions.
To answer these questions we need a benchmark of real-world functions with known obligation profiles and a complexity-controlled comparison set. Existing benchmarks such as TestGenEval
(
Jain et al., 2025
)
evaluate test generation quality using aggregate metrics but do not provide obligation-level annotations together with a complexity-stratified comparison set. We therefore introduce ObligBench, a Java benchmark derived from The Stack v2
(
Lozhkov et al., 2024
)
. It comprises 895 complex functions under test, selected from the top 5% by cyclomatic
(
McCabe, 1976
)
and cognitive
(
Campbell, 2018
)
complexity, and a low-complexity control set of 700 functions. In the main experiment, we evaluate four LLMs (GPT-5.4, Gemma-4-31B, Gemini-3.6-flash, and Qwen3-Coder-30B) under four prompting strategies (zero-shot, intention-planning, mutation-feedback, and Panta
(
Gu et al., 2026
)
) on the 895 complex functions, yielding 14,320 generated tests for RQ1-RQ4. For RQ5, we additionally evaluate tests generated for the 700-function low-complexity control set.
Our results reveal systematic adequacy blind spots that aggregate coverage and mutation scores do not distinguish. LLM-generated tests struggle most with inputs requiring semantic reasoning about the function’s contract, as null inputs are covered in only 34.8% of applicable cases, negative inputs in 23.8%, and empty inputs in 38.8%. The same happy-path bias appears in control-flow adequacy, with scores of 0.100 for catch blocks and 0.312 for default groups, as reaching these constructs requires deliberately out-of-domain inputs that LLMs tend to avoid. Taken together, these patterns show that LLMs exhibit the happy-path bias long observed in human-written test suites
(
Barr et al., 2015
;
Beller et al., 2015
)
that, attention is concentrated on normal inputs and expected execution flows, while unusual values and exceptional paths are systematically omitted, forming blind spots that aggregate metrics do not surface. On the assertion side, oracle strength is high overall but weak for object returns when concrete default mutation can be made, where models default to coarse checks rather than field-level value assertions. presents the full results for all five research questions.
This paper contributes:
(1)
Evaluation framework.
BlindSpotEval
combines an executability assessment with three AAA-aligned adequacy metrics (BVA, CFA, and OS). It characterizes execution failures before adequacy scoring and produces construct-level profiles that identify under-tested obligation types, supporting targeted improvements to generated tests.
(2)
Benchmark.
ObligBench
comprises 895 complex and 700 low-complexity real-world Java functions under test (FUTs), with source-side obligation annotations and immutable-FUT constraints.
(3)
Empirical study.
An evaluation of four LLMs under four prompting strategies, comprising 14,320 generated tests on complex functions, characterizes execution failure modes and identifies recurring gaps in boundary-value coverage, exceptional control flow, and oracle strength. An additional study on 700 low-complexity functions indicates that these patterns are more pronounced in complex functions but also occur in simpler code. All artifacts are publicly available.
2.
Background and Related Work
LLM-based test generation.
Automated unit test generation has a long history of search-based
(
Harman and Jones, 2001
;
Fraser and Arcuri, 2011
;
Panichella et al., 2018
)
, random
(
Pacheco et al., 2007
)
, and symbolic-execution
(
King, 1976
;
Cadar et al., 2008
)
approaches. Anand et al.
(
Anand et al., 2013
)
survey these methods before the emergence of LLM-based techniques. More recently, LLMs have become a prominent approach to test generation, both independently and in combination with established techniques. AthenaTest
(
Tufano et al., 2020
)
formulates test generation as a sequence-to-sequence learning task, using pretraining followed by supervised fine-tuning on focal-method–test pairs. ChatUniTest
(
Chen et al., 2024
)
combines adaptive focal context with a generation-validation-repair workflow. TestPilot
(
Schäfer et al., 2024
)
refines failing tests using execution errors, while CoverAgent
(
CodiumAI, 2024
)
iteratively generates and validates tests to improve code coverage. CodaMosa
(
Lemieux et al., 2023
)
invokes an LLM to overcome coverage plateaus in search-based generation. MuTAP
(
Dakhel et al., 2024
)
uses surviving mutants to augment prompts for further test generation. ChatTester
(
Yuan et al., 2024
)
combines intention-based generation with iterative repair guided by compilation errors and additional code context. Panta
(
Gu et al., 2026
)
integrates static control-flow analysis and dynamic coverage feedback to identify under-tested execution paths and guide subsequent generation. In an industrial setting, Alshahwan et al.
(
Alshahwan et al., 2024
)
introduce TestGen-LLM, which extends existing tests and filters generated candidates for build success, execution reliability, and coverage improvement. These approaches commonly assess effectiveness through compilation or execution success, structural coverage, or aggregate mutation scores.
BlindSpotEval
complements these measures with obligation-level profiles that distinguish adequacy across input categories, control-flow constructs, and assertion targets.
Test adequacy criteria.
Structural criteria, including line coverage, branch coverage, and modified condition/decision coverage (MC/DC), assess the execution of code elements and satisfaction of decision-related coverage requirements
(
Ammann and Offutt, 2016
;
Zhu et al., 1997
)
. Mutation testing introduces artificial faults and assesses whether tests detect the resulting changes
(
DeMillo et al., 1978
;
Offutt and Untch, 2001
;
Jia and Harman, 2011
;
Coles et al., 2016
;
Tip et al., 2025
)
. Although both approaches provide detailed information, their aggregate scores do not directly distinguish adequacy across input categories, construct types, and assertion targets. Prior work examines limitations of structural coverage
(
Goodenough and Gerhart, 1975
;
Inozemtseva and Holmes, 2014
)
, its relationship with mutation-based test generation
(
Fraser and Arcuri, 2015
)
, and the detection of real faults by generated tests
(
Shamshiri et al., 2015
)
. Other studies investigate whether mutation analysis reflects real-fault detection
(
Andrews et al., 2005
;
Papadakis et al., 2018
)
. For LLM-generated tests, a replicability study finds that the usefulness of coverage and mutation scores depends on the evaluation setting
(
Zhao et al., 2026
)
.
Boundary-value analysis emphasizes inputs at and around the boundaries of equivalence partitions
(
Myers et al., 2011
;
Ammann and Offutt, 2016
)
. Category-partition testing similarly organizes the input space into categories and choices
(
Ostrand and Balcer, 1988
)
. Our
Boundary-Value Adequacy
(BVA) metric operationalizes these ideas through statically extracted per-parameter obligations. A boundary category receives credit only when the corresponding value is supplied at the relevant parameter position, allowing gaps to be attributed to specific categories and parameters.
Extreme mutation identifies pseudo-tested methods whose implementation logic can be removed without causing test failures
(
Niedermayr et al., 2016
)
. Vera-Pérez et al.
(
Vera-Pérez et al., 2019
)
extend this work through a broader empirical study of pseudo-tested methods. Our
Control-Flow Adequacy
(CFA) metric instead targets individual control-flow constructs, attributing gaps to specific exception handlers, default branches, and throw paths.
For oracle evaluation, Barr et al.
(
Barr et al., 2015
)
survey the broader test oracle problem. Schuler and Zeller
(
Schuler and Zeller, 2013
)
introduce checked coverage, which uses dynamic slicing to identify executed statements that influence an oracle. Just et al.
(
Just et al., 2014b
)
find an empirical relationship between mutant detection and real-fault detection, supporting mutation analysis as a proxy under the studied conditions. Our
Oracle Strength
(OS) metric assesses assertion-based detection of mutations to return values and exception behavior. It gives incidental kills caused by unexpected exceptions or crashes no credits and reports scores by assertion subcategory, distinguishing oracle strength for object returns, exception behavior, and scalar values.
Benchmarks for automated test generation.
Established benchmarks such as SF110
(
Fraser and Arcuri, 2014
)
and Defects4J
(
Just et al., 2014a
)
support the evaluation of test generation and fault detection and predate the recent use of LLMs for these tasks. More recent benchmarks draw on repositories and curated code corpora.
ULT
(
Huang et al., 2025
)
provides curated function-level tasks involving complex Python functions, with an emphasis on mitigating test contamination. Its paired benchmark, PLT, supports comparisons with a setting in which reference tests are exposed. TestGenEval
(
Jain et al., 2025
)
provides code–test file pairs for full-file test generation and test completion, evaluated through execution success, coverage, and mutation scores. Other benchmarks address related objectives. EvalPlus
(
Liu et al., 2023
)
augments HumanEval with more extensive test inputs to evaluate the functional correctness of generated code, while SWE-bench
(
Jimenez et al., 2024
)
targets repository-level issue resolution. These resources do not jointly provide source-side obligation annotations and a complexity-stratified comparison set for evaluating generated unit tests.
ObligBench
provides both through real-world Java functions drawn from The Stack v2
(
Lozhkov et al., 2024
)
, complexity-based selection, and source-side obligation annotations. Its evaluation protocol requires function bodies to remain unchanged so that adequacy is assessed against a fixed implementation.
3.
ObligBench Construction
Existing test-generation benchmarks evaluate quality through aggregate metrics and do not jointly provide obligation-level annotations and a comparison set spanning different levels of complexity. To surface blind spots at the obligation level across all three AAA dimensions, we construct ObligBench from The Stack v2
(
Lozhkov et al., 2024
)
, a large licensed source-code corpus. We focus on Java because its explicit method signatures and mature analysis and testing ecosystem, including JaCoCo and PIT
(
Coles et al., 2016
)
, support self-containment validation and obligation-level analysis.
Adapting the multi-stage construction approach of ULT
(
Huang et al., 2025
)
, we select functions under test (FUTs) by complexity, and validate both high-complexity and low-complexity sets for self-containment and leakage before generation as discussed below.
Complexity-guided non-trivial FUT selection.
We select non-trivial FUTs using two complementary complexity metrics: (1) Cyclomatic complexity (CycC)
(
McCabe, 1976
)
counts independent execution paths, and (2) cognitive complexity (CogC)
(
Campbell, 2018
)
additionally penalizes nesting and flow interruptions. Together, these metrics capture different aspects of control-flow complexity and provide a basis for selecting functions with varied test-generation demands.
We use the top 5% under each metric to define two overlapping high-complexity views. In our hydrated Java sample, these thresholds are
CycC
≥
8
\mathrm{CycC}\geq 8
and
CogC
≥
13
\mathrm{CogC}\geq 13
. Each view contains 700 tasks, of which 505 occur in both views. We retain the overlap and record view membership for each task so that subsequent analyses can account for the shared functions. The deduplicated union of 895 functions forms the
treatment set
used in the main evaluation across LLMs and prompting strategies.
For RQ5, we additionally construct a 700-function
control set
with scores below both thresholds (
CycC
<
8
\mathrm{CycC}<8
and
CogC
<
13
\mathrm{CogC}<13
). Both sets undergo self-containment validation and together constitute
ObligBench
. The control set is used only for the complexity comparison in RQ5.
Self-containment.
To enable test generation and execution without full repository context, we package each accepted function as an isolated executable Java task. The FUT body remains unchanged throughout this process, enforced by AST-token signature comparison against the original source. Each task passes a three-stage filter: parsing and type extraction, a smoke test that compiles the task and executes three distinct invocations, and an LLM wrapper-generation fallback for fixtures that fail to compile or execute.
Test leakage check.
Pre-existing tests in the corpus would give LLMs an unfair retrieval advantage
(
Shi et al., 2024
)
. Following ULT
(
Huang et al., 2025
)
, we check for existing tests associated with each FUT in the source corpus. We identify test-like files from the same Stack v2 repository and revision using path and content patterns, including
/test/
,
*Test.java
,
@Test
, and common JUnit or TestNG imports. Our check is a deterministic filter over the hydrated cache, and we flag a candidate only if it references the focal method, class, or package with sufficient heuristic evidence. In ObligBench, no likely corresponding Stack v2 tests were found for any of the 895 unique tasks.

4.
Evaluation Metrics
Our research questions demand metrics that go beyond aggregate execution, coverage, and mutation scores. A test may execute successfully, cover branches, and kill mutants while still omitting important inputs, failing to check observable obligation, or asserting only coarse properties
(
Barr et al., 2015
;
Hossain et al., 2023
;
Jahangirova et al., 2016
)
. Aggregate metrics summarize test performance but do not directly identify which behavioral obligations remain unchecked. We therefore define a set of deterministic adequacy metrics that characterize complementary dimensions of generated-test behavior and produce construct-level profiles.
The proposed metrics follow the Arrange-Act-Assert (AAA) structure commonly used to organize unit tests
(
Osherove, 2014
;
Meszaros, 2007
)
. We measure
Boundary-Value Adequacy
(Section
4.3
), which characterizes the inputs a test arranges;
Control-Flow Adequacy
(Section
4.4
), which characterizes the behavioral branches the test reaches and distinguishes; and
Oracle Strength
(Section
4.5
), which whether tests check return values and exception behavior through targeted mutations. Each metric is
computed per generated test per FUT, and aggregate results are reported by model and prompting strategy. We refer to each test–FUT evaluation instance as a
row
.
The three metrics use different measurement procedures.
BVA statically identifies selected input categories from the test source, independently of assertion quality.
CFA and OS use targeted mutations and test execution to assess detection, and they are not independent: an obligation the test never reaches
scores zero in CFA and is excluded from the OS denominator, so test suites with poor CFA may still have good OS. We report the eligible-obligation count
alongside OS summary scores. We first describe the shared obligation scoring pipeline, then define each metric in turn.
4.1.
Mutation-Based Obligation Scoring Pipeline
CFA and OS both score obligations by mutation: for each obligation, we construct mutants whose
survival
implies the obligation was not exercised or not checked. This differs from classical mutation testing, which reports a single aggregate kill count treating equivalent mutants as noise
(
Papadakis et al., 2019
)
. Here, we score by the stage where obligation belongs (arrange, act or assert), and the corresponding obligation must be killed, incidental kills do no contribute the scores. Two design choices distinguish our scoring: mutants are attributed to individual obligations and scored per-obligation, and unrepresentable obligations are excluded from adequacy denominators, with CFA additionally reporting a
representativeness rate
to indicate tooling gaps.
The CFA and OS scoring pipeline separates into two stages: (1)
collectors
generate mutants, compile and execute them, and write versioned artifacts, and (2) an
analyzer
consumes those artifacts and computes scores without rerunning mutations.

4.2.
Execution Reliability: Pre-Scoring Failure Classification
We evaluate generated tests in a regression-testing setting, treating the original FUT as the reference implementation. Before adequacy scoring, we identify compilation failures, execution failures, and fixed placeholder outputs. These rows receive explicit skip statuses and are retained for reporting exclusion rates.
Compile failures
arise when the test cannot be compiled due to private-field access, unresolved symbols, type mismatches, checked-exception violations, or syntax errors.
Execution failures
arise when the test compiles but does not reach a clean end state. Subcategories include uncaught runtime exceptions and timeouts. We separately identify
wrong-oracle failures
, in which an assertion specifies an expected result inconsistent with the reference implementation. Line and branch coverage may still record the code executed before the assertion fails, so coverage scores alone do not establish whether the generated test passes.
Generation failures
include Panta’s fixed placeholder output, identified by its placeholder marker and small stub structure. This output contains a vacuous
assertTrue(true)
assertion and provides no meaningful oracle signal. Although it may compile and execute, it is excluded before adequacy scoring. Treating these as executable tests would silently inflate adequacy-rate denominators without contributing any oracle signal.
4.3.
Boundary-Value Adequacy: the Arrange Phase
Boundary-value analysis emphasizes inputs at and around important partitions of the input domain. We define Boundary-Value Adequacy (BVA) as a parameter-specific input-space metric. A boundary category is credited only when it is used for the corresponding parameter in a generated call to the FUT.
Applicable boundary obligations.
For each FUT, we infer applicable boundary obligations from its signature and simple source-level constraints.
There are 11 boundary categories: null, empty, false_value, true_value, zero, negative, below_inferred_bound, at_inferred_bound, above_inferred_bound, same_inferred_bound, and different_inferred_bound.
Signature-derived categories follow the declared type. Reference parameters receive a
null
obligation, strings and collections or arrays receive an
empty
obligation, numeric parameters receive
zero
and
negative
obligations, and boolean parameters receive obligations for both values.
The inferred-bound categories are source-derived, each direct parameter–literal comparison in the FUT body, such as
x < 5
, introduces
below
,
at
, and
above
obligations for that bound. Different inferred bounds are retained separately. String equality comparisons introduce an equality obligation for each inferred literal and a difference obligation requiring a value unequal to all inferred literals for that parameter. 4.5.
Oracle Strength: the Assert Phase
Branch coverage and standard mutation score both treat a test as adequate regardless of whether its assertions verify the exact resulting behavior. A test can achieve full branch coverage without asserting or asserting only that the function does not throw, leaving its actual result entirely unchecked. Even when meaningful assertions are present, kills can be incidental. A mutation may produce an unexpected exception and PIT records a kill, while the obligation was never intentionally checked. Oracle Strength (OS) addresses this blind spot by scoring each assertion obligation via targeted mutation that isolates changes to the asserted value.

7.
Threats to Validity
Construct validity.
BVA uses deterministic static analysis, and 29.3% of the target-call arguments cannot be resolved by the supported analysis rules. We report this proportion explicitly to distinguish the scope of input resolution from the adequacy of the generated tests. The manual validation described in Section
4.6
assesses the reliability of the resulting classifications.
Internal validity.
The choice of CFA mutation operators may influence the measured adequacy of different control-flow constructs. We address this through deterministic, construct-specific transformations applied
uniformly across models, strategies, and complexity sets. We also report representativeness rates alongside adequacy scores, distinguishing limitations in mutant availability from failures to detect represented behavioral changes.
External validity.
The blind-spot patterns are consistent across all four models from different families and four different strategies, reducing the risk that any single model or prompt design drives the results.
Results may differ for very small models, domain-specialized code models, or prompt designs not studied here. All generation uses temperature 0, results under non-zero temperature may show
higher variance.
8.
Conclusion
We propose
BlindSpotEval
, an obligation-based evaluation framework for LLM-generated unit tests, evaluating tests through Boundary-Value Adequacy, Control-Flow Adequacy, and Oracle Strength, complemented by execution reliability and failure-mode analysis.
We also introduce
ObligBench
, a complexity-stratified Java benchmark of 895 complex and 700 low complexity FUTs with source-side obligation annotations.
Applied to 14,320 generated tests across four LLMs and four prompting strategies on ObligBench treatment set,
BlindSpotEval
reveals systematic blind spots that aggregate coverage and mutation scores do not distinguish.
Execution reliability is the first barrier, with 72.1% of generated-test rows eligible for adequacy analysis. Wrong-oracle failures account for 15.6% of excluded rows, demonstrating that executed code can receive coverage credit even when generated assertions fail.
Beyond execution, the dominant weakness is out-of-domain value reasoning and bias to happy path.
Boolean and inferred-bound BVA categories are near-ceiling across all models and
strategies, whereas
null
,
negative
, and
empty
obligations reach only 34.8%, 23.8%, and 38.8%, for which the boundary values are not directly inferrable from the source code.
These omissions, together with low CFA for
catch
blocks (0.100) and
default
groups (0.312), are consistent with a happy-path preference in generated tests.
Obligation-based control-flow mutations broaden construct-level evaluation, particularly for explicit throw obligations, which achieve 98.2% representativeness compared with 1.4% under the configured PIT analysis. Separate forced-outcome mutations also distinguish partial checking of conditional alternatives that an any-kill indicator does not express.
Oracle Strength further distinguishes meaningful checking from incidental execution failures. Although return obligations score 0.842 overall, concrete-constructor-defaults obligations score only 0.325, exposing a pronounced gap in detecting changes to constructed object state. Exception obligations score 0.625, further distinguishing the ability to reach exceptional behavior from the ability to check it.
The low-complexity comparison shows that selected boundary-value and control-flow blind spots also occur in simpler functions, while well-supported OS categories remain strongly checked across both complexity sets. Across the study, obligation-level profiles identify the input categories, control-flow constructs, and observable behaviors that require stronger testing.
Together, these findings motivate shifting from aggregate coverage and mutation scores to construct-level adequacy profiles that reveal
where
generated tests leave behavioral obligations unchecked and guide targeted improvements.
