# Interim report: label-and-data-feasibility

**Locus question:** On single-GPU 7B compute and a tight timeline, which label mechanism (zero-sample proper-scoring vs N=100 MC-sample vs K-sample DPO) and how many code problems are needed to train discriminative confidence without repeating the 274-example collapse?
**Flavor:** technical (feasibility gate)

## What the corpus already said

The width sweep had already flagged the three candidate label mechanisms at a high level: ConfTuner needs zero extra sampling, Uncertainty Distillation (UD) needs ~N=100 Monte Carlo samples/question, and ORCE needs K samples/prompt to build a rank-based DPO reward — but none of the width-stage summaries had pulled the actual compute-appendix numbers, and none had connected these mechanisms to the base paper's own diagnosis of *why* the 274-example SFT collapsed. The query grounding file states the collapse precisely: LoRA r=16 SFT on 274 examples reduced verbal ECE by 64% but produced "calibration without discrimination" — mean confidence 0.900 assigned to both easy and hard problems, i.e. the output distribution collapsed to one default bin. That is consistent with a discrete/coarse target (a 1–5 Likert bin) trained via cross-entropy on too little, too-imbalanced data — a classic majority-class collapse — but the corpus had not yet tested that diagnosis against alternative loss/label designs.

## What the new sources say

**ConfTuner** ([[conftuner-training-large-language-models-to-express-their-confidence-verbally]]) trains a "tokenized Brier score" loss — a proper scoring rule applied directly to the next-token distribution over confidence levels 0–100 — using only the binary correctness of a single generated answer, no sampling, no proxy score. Its own efficiency appendix is the most load-bearing single fact I found for this locus: *"training was conducted on 4 A40 GPUs and inference on a single A40 GPU... ConfTuner requires less training and inference time, and fewer training samples than training-based baselines... ConfTuner converges to optimal performance with merely 2,000 training samples."* Appendix D.1 adds: *"It takes about 4 minutes for training and 1 minute for inference."* LoRA config: rank 8, alpha 32, applied to Q/V projections only, 2–3 epochs, batch size 16–24, lr ~1e-5–3e-5. This is a single-model, single-forward-pass design — exactly matching the single-GPU constraint — and it is a proven, reproducible, minutes-scale training recipe at 2,000 examples.

**Uncertainty Distillation** ([[uncertainty-distillation-teaching-language-models-to-express-semantic-confidence]]) is the cautionary data point on sampling cost. Its own resource-reporting appendix states: *"Sampling for SQUAD took a total of 60 GPU hours on NVIDIA-V100s; for SNI took 45 GPU hours on NVIDIA-A100s; for SocialIQA took 350 hours on NVIDIA-A100s; for MMLU took 350 hours on NVIDIA-A100s; for GSM8k took 80 hours on NVIDIA-A100s."* These are N=100-per-question sampling costs over FULL training sets of tens of thousands of questions (e.g. SocialIQA train ≈ 33,410 examples), and — critically — UD's label pipeline requires pairwise semantic clustering (NLI entailment or exact-match) across the 100 samples per question, which is itself GPU-forward-pass-heavy. Scaling this appendix number (≈0.377 sec/completion, entailment-inclusive) down to a 2,000–4,000-problem code corpus at N=10–100 gives the GPU-hour table in the synthesis section below. UD's own reported discrimination ceiling (AUROC 0.69–0.79 across MMLU/SocialIQA/GSM8K) is also notably far below the base paper's n=10 sampling-signal AUROC of 0.987 for code — a gap I return to in the committed position.

**ORCE** ([[orce-order-aware-alignment-of-verbalized-confidence-in-large-language-models]]) trains a *separate* confidence LLM via DPO against a Spearman-rank-correlation reward derived from K sampled completions of the (frozen) answer model. Its own Appendix C.1 states plainly: *"All experiments are conducted on a compute node equipped with 128 CPU cores... and 4 NVIDIA H100 GPUs with 80GB HBM3 memory each"* and *"we first train the supervised fine-tuning (SFT) model for 3 epochs and then further optimize it with reinforcement learning for 3 epochs. For both MMLU and DROP, we randomly sample 10,000 training examples for SFT and 20,000 training examples for RL."* This is roughly an order of magnitude beyond the query's single-A100/single-GH200 constraint (4×H100 vs 1 GPU) and beyond the 274-example-collapse-driven data scale the project is trying to fix cheaply. ORCE's own gap analysis (in the width-stage summary) explicitly flags that "a genuinely single-model, single-forward-pass distillation... remains open" — ORCE is not designed for this compute envelope.

**ConSelf** ([[self-improving-code-generation-via-semantic-entropy-and-behavioral-consensus]]), while not a confidence-elicitation paper, is the single most directly comparable compute precedent: it runs LoRA DPO (rank 16, alpha 32, batch 16, lr 5e-6, seq len 2048, K=15 candidates/problem via n_code=5 samples × 3 observations) on **a single NVIDIA A800 GPU**, using **DeepSeek-Coder-6.7B-Instruct and Qwen2.5-Coder-7B** — the exact model family the base paper uses — with a curated training set of 6,372 examples (successfully outperforming unfiltered Self-DPO on 46,734 examples, which actively *degraded* the same base models). This is strong evidence that (a) single-GPU DPO/SFT at few-thousand-example scale is a proven, working recipe on these exact model families, and (b) more raw data is not automatically better — curated subsets beat larger noisy ones, which bears directly on how to grow past 274 examples without over-diluting signal quality.

**Verification Limits Code LLM Training** (Cohere, [[250920837-verification-limits-code-llm-training]]) establishes the "verification ceiling": when both problems and tests are LLM-generated, training data quality is bottlenecked by the verifier's own capability; rigid 100%-pass-all-tests filtering discards valuable diversity (relaxing thresholds or using soft LLM verification recovers 2–4 pass@1 points), but verification "cannot be discarded, only recalibrated." This risk is specifically about *synthetic* problems/tests, not human-authored benchmark tests — a distinction that matters directly for the data-sourcing decision below.

**vLLM v0.6.0 benchmarks** ([[vllm-v060-27x-throughput-improvement-and-5x-latency-reduction-vllm-blog]]) and **Raschka's LoRA wall-clock post** ([[practical-tips-for-finetuning-llms-using-lora-low-rank-adaptation]]) were fetched to sanity-check the generation and training throughput assumptions independent of the confidence-elicitation papers. The vLLM post's directly-extractable figure (Llama-3-8B, H100, light load) is ~77 tokens/sec **single-stream**; batched aggregate throughput on a 7-8B model is well documented elsewhere in the vLLM ecosystem to reach the 2,000–5,000 tok/s range on A100/H100-class GPUs, consistent with the UD-anchor-derived per-completion cost used below. Raschka's post reports a full 50k-example Alpaca LoRA run (7B Llama-2, single A100, rank 8, seq len 1304) at **1.85 hours**; per-example cost is roughly linear, so a 2,000–8,000-example run on the same hardware scales to well under an hour to ~15–20 minutes at the low end — corroborating ConfTuner's own reported "4 minutes" training time at 2,000 examples.

## Evidence synthesis

**GPU-hour math for label-building (generation only).** Using UD's own SocialIQA appendix figure (350 GPU-hours / (33,410 questions × 100 samples) ≈ 0.377 sec/completion, which *includes* NLI-based semantic-clustering overhead) as an anchor, and discounting ~20% for the fact that code-equivalence clustering can be done via test execution/output-diffing (cheap CPU work) rather than a second GPU forward pass for NLI entailment:

| Training pool size | N=10 (matches base paper) | N=20 | N=100 (UD default) |
|---|---|---|---|
| 2,000 problems | ~1.7 GPU-hr | ~3.4 GPU-hr | ~16.8 GPU-hr |
| 4,000 problems | ~3.4 GPU-hr | ~6.7 GPU-hr | ~33.5 GPU-hr |
| 8,000 problems (w/ APPS) | ~6.7 GPU-hr | ~13.4 GPU-hr | ~67.0 GPU-hr |

LoRA training itself is cheap regardless of label mechanism: ConfTuner's own reported "4 minutes" at 2,000 examples, and Raschka's linear-scaling extrapolation (well under 1 hour for 2,000–8,000 examples on a single A100), both point to training cost being a rounding error next to label-generation cost. ORCE's SFT+RL stages (3+3 epochs on 10k–20k examples on 4×H100) are the one data point that breaks this pattern — but that cost is a function of ORCE's *decoupled two-model DPO/RL architecture*, not of dataset size alone, which is exactly why ORCE is the wrong architecture to import here.

**The central tension worth naming explicitly:** the base paper's own diagnostic result is that n=10 sampling *already* achieves AUROC 0.987 for code — near the discrimination ceiling. UD's N=100 design exists because QA/reasoning tasks have a much noisier, lower-ceiling sampling signal (UD's own reported AUROC 0.69–0.79) that needs more samples to denoise. Code has a structurally different reliability oracle: execution gives a crisp, low-noise binary pass/fail per sample, so the marginal information gained from sample 11 through 100 is small once n=10 already saturates near 0.987. This means N=100 is technically *affordable* (16.8–67 GPU-hours, well within budget) but likely *wasteful* relative to what the evidence suggests code needs — the corpus gives no reason to expect N=100 to out-discriminate N=10 for code, only reason to expect it costs ~10x more.

**The likely actual cause of the 274-example collapse**, reading ConfTuner and the base paper together, is two compounding factors: (1) too little data (274 examples vs ConfTuner's own reported 2,000-example convergence point) and (2) a coarse discrete-bin cross-entropy target rather than a proper scoring rule. ConfTuner's theoretical result — that training against a tokenized Brier score is *itself* a proper scoring rule, so the loss-minimizing model provably places probability mass at the true conditional correctness probability — is a mechanism-level, falsifiable fix for exactly the failure mode described (majority-bin collapse under label/data scarcity). No source in this corpus has tested this specific loss on code, which is the paper's actual novelty gap and this locus's biggest unresolved risk.

## Committed position

The recommended label mechanism is a **hybrid**, not a straight import of any one paper: use ConfTuner's zero-extra-sample tokenized-Brier-score training objective, but retarget it from ConfTuner's own binary single-generation-correctness label onto the **continuous n=10 execution pass-rate** the base paper already computes as its AUROC-0.987 internal signal — i.e., distill the paper's own strongest evidence source into a single-forward-pass verbalized output via a proper scoring rule, instead of the coarse 1–5-bin cross-entropy that most plausibly caused the 274-example collapse. This design needs no incremental sampling cost beyond what n=10 pass-rate computation already requires (reuse, don't resample), needs no second confidence model (unlike ORCE, ruling out its 4×H100/10k–20k-example compute footprint), and is cheap enough (≈1.7–6.7 GPU-hours generation + <1 hour LoRA training for a 2,000–4,000-problem pool) to leave a wide margin inside 10 days. Do **not** adopt UD's full N=100-per-training-problem design as primary; use it only as a small (~300-problem) diminishing-returns ablation (N∈{5,10,20,50,100} vs AUROC) that is itself a defensible, cheap (~2–3 GPU-hour) supporting-result panel showing code's sampling signal saturates well below N=100 — this doubles as a direct empirical rebuttal of "just use UD's recipe" from Layer 5 critics. Source the training pool from MBPP (974, human-written tests) plus a filtered APPS subset (≥3 test cases/problem to dodge the Cohere verification-ceiling risk) plus a LiveCodeBench train-window release, targeting 2,000–4,000 problems total — comfortably clearing ConfTuner's own reported 2,000-example convergence floor without touching synthetic problem generation, which avoids the verification-ceiling risk entirely for the primary dataset (that risk only reactivates if synthetic problems are later added to pad corpus size, in which case Cohere's relaxed-threshold/soft-verification mitigations should be applied rather than rigid 100%-pass filtering). Hold out HumanEval (164, the base paper's original data) and a separate LiveCodeBench release window purely for evaluation to avoid contamination.

- **Position:** The headline experiment — SFT a 7B code model with a ConfTuner-style proper-scoring loss against the paper's own n=10 execution-pass-rate signal, on a ≥2,000-problem pool drawn from MBPP+APPS+LiveCodeBench, evaluated on held-out HumanEval+LiveCodeBench — is achievable on a single A100-40GB/GH200 within the 10-day window, with an estimated 15–25 GPU-hours for one clean pass (label generation + LoRA training + eval sampling + the N-sweep ablation + 2–3 baseline reproductions), and roughly 45–75 GPU-hours with a realistic 3x buffer for debugging and reruns — comfortably inside a 10-day budget even at conservative ~5–6 active GPU-hours/day. **Verdict: YES**, for this de-scoped, single-model design. ORCE's decoupled two-model K-sample DPO architecture and UD's full N=100-on-the-entire-training-pool design should both be explicitly ruled OUT as the headline (not just de-scoped) given the 10-day/single-GPU constraint — ORCE by a full order of magnitude in compute footprint, UD's full-N=100 by opportunity cost against a signal that's already near-ceiling at N=10.
- **Confidence:** medium-high. The label-mechanism recipe (ConfTuner's proper-scoring loss, LoRA config, minutes-scale training, 2,000-example convergence floor) is drawn directly from published compute appendices, not extrapolation. The GPU-hour estimate for code-specific N-sample generation is an extrapolation from a QA paper's appendix figure adjusted for an assumed (not directly measured) removal of NLI-clustering overhead — reasonable but unverified for code specifically. The single biggest unvalidated leap is the hybrid objective itself (ConfTuner's loss + the base paper's n=10 pass-rate target, applied to code): no source in this corpus tests this exact combination, so it is a design proposal grounded in mechanism, not a replication.
- **Boundary conditions:** This verdict holds for a single-model, single-forward-pass, proper-scoring SFT design trained on ≤4,000 real (non-synthetic) code problems with n≤20 samples/problem. It does NOT hold for: (a) any design requiring a second decoupled confidence model (ORCE-style) under this compute budget; (b) N=100-per-problem sampling applied to the FULL training pool rather than a small ablation subset, which is technically feasible but a poor use of the 10-day budget; (c) any plan that requires synthetic problem generation to hit data-volume targets, where the Cohere verification-ceiling risk reactivates and is unquantified here.
- **What would change this position:** If a fast pilot (Day 1–2, ~200–300 problems) shows the ConfTuner-style hybrid loss ALSO collapses to a near-constant confidence output despite the graded, proper-scoring target — that would falsify the "coarse label + data starvation" diagnosis of the 274-example collapse and point instead to a deeper representational limit (consistent with the sibling locus's finding that self-report fails broadly across architectures), at which point the plan should pivot toward ORCE's decoupled-head architecture even at higher compute cost, or toward a narrower claim. Separately, if sandboxed test-execution infrastructure (not GPU time) turns out to need more than 1–2 days of wall-clock to run 40,000–800,000 test executions even with reasonable parallelization, the 10-day timeline verdict flips from YES to a further-de-scoped version (smaller problem pool, N=5–10 only, no ablation sweep).
- **Evidence weight:** 3 direct compute-appendix data points support cheap single-GPU feasibility for the ConfTuner-style, single-model design (ConfTuner: 4 min/2,000 examples/4×A40; ConSelf: single A800, DPO on 6,372 curated examples, matching model families; Raschka: 1.85h/50k examples on single A100, linear-scaling). 1 direct compute-appendix data point (ORCE: 4×H100, 10k–20k SFT/RL examples) contradicts feasibility of the decoupled-DPO alternative under this budget. 1 extrapolated (not directly measured) estimate, anchored to UD's own appendix numbers, supports N=10 as cheap and N=100-on-the-full-pool as expensive-but-technically-feasible-and-low-expected-value for code specifically. 0 sources directly validate the proposed hybrid loss+label-target combination on code — this is the paper's actual bet, not something this locus can de-risk further without running the Day-1–2 pilot named above.

## Open questions

- No source in-corpus reports code-specific N-sample generation throughput or code-specific semantic/execution-clustering GPU cost directly — the GPU-hour table above is an extrapolation from a QA paper's appendix, not a code benchmark. A quick internal pilot (time 50 completions on the target model/GPU) would collapse this uncertainty in under an hour and should be the very first thing run.
- Exact current size of the LiveCodeBench train-window release and how many APPS problems survive a ≥3-test-case filter were not pulled from primary sources within this locus's 5-source budget — both are needed to finalize the exact problem-pool composition before Day 1.
- Whether the n=10 protocol's AUROC 0.987 is sensitive to HumanEval's "skewed easy difficulty distribution" (a limitation the base paper itself flags) was not re-examined here; if the new training pool (MBPP/APPS/LiveCodeBench) has a harder difficulty mix, the n=10-samples-suffice assumption should be re-validated on that pool specifically before committing to N=10 as final.
