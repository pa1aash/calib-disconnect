# Masked-LoRA stated-confidence readout: adversarial review

Scope: `pipeline/readouts/masked_lora.py`, its callers (`lora_train.py`, `recipe.py`, `adapter_readout.py`, `real_backend.py`, `rtuning.py`, `stage.py`, `isotonic.py`), tests in `tests/readouts/`, contracts in `pipeline/contracts/interfaces.py` and `constants.py`, against `docs/s7/PIPELINE_DESIGN_FROZEN.md` sections 7.3, 7.4, 7.11, 7.12, 12.5, and 13 (K4).

Test run: NOT RUN. This review session had no shell tool, so `uv run pytest tests/readouts -q -k "mask or kv or lora"` was not executed. Every statement below about test behavior comes from reading the code, not from a test run. Findings marked "suspected" were not confirmed by running anything.

## Answers to the seven questions

1. **Is the LoRA delta zero off the span?** Yes, by construction, for the left-padded layout. A forward hook on every `lora_B` multiplies the branch output by the per-token mask (masked_lora.py:204-207, 280). The code checks that the hook count equals the target count (masked_lora.py:195-196), and the targets cover all seven projections in every decoder layer (masked_lora.py:50, 80-89). Pad columns have mask 0 (masked_lora.py:129-135). The economy path runs the prefix in "off" mode and the elicitation tokens with mask ones, using the base prefix cache (masked_lora.py:299-307). Right padding is never built, never supported, and never tested, and `final_state` hard-codes column -1 (finding m6). There is one theoretical gap: the multiplicative mask is not exact for non-finite values (m7).
2. **Is the prefix KV cache identical, and is the adapter nonzero?** In the full masked forward, check (a) compares the KV cache at every non-masked, non-pad position across all layers (masked_lora.py:414-423). The adapter is nonzero (`init_std=0.1`), and (b) confirms this. The separate "prefix cache" check (c) is tautological (m8). The economy cache is the base cache by construction ("off" mode).
3. **Does the positive control fail when it should?** By reading, yes: it would fail for a zero adapter or a zero mask. No test exercises that failure (m9). The leaky-mask control for (a) is tested (test_readouts_masked_lora.py:51-64). Neither control can detect a wrong span definition, because both compare against the same mask they apply (M3).
4. **Is the readout at p3, in float32, with the variant-set log-sum-exp?** Yes (masked_lora.py:295-321). The LM-head rows are applied in float32, soft-capping is applied before the log-sum-exp, and the normalizer cancels. Two caveats: the Yes and No ids the real backend loads crash on the generate-stage file format (B1), and the LM-head bias is handled differently from the capture engine (m4).
5. **Do training and selection match the design?** BCE, AdamW, cosine with 5 percent warmup, effective batch 64, 2 epochs, eval every 20 steps, step transfer by epoch fraction with the schedule compressed, and K4 retry and flagging all match. The exceptions are m1, m2, m3, and M5 (schedule mismatch in the reused split-0 scores), plus missing reuse of recipes across checkpoints (M2) and a probe-side K4 retry that was not located (M4).
6. **Can test-fold labels leak?** No path was found. Selection uses inner split 0 of the outer-train rows (recipe.py:158-174). The final fit has no eval rows and scores the test fold only after training (recipe.py:221-226). The isotonic map uses inner or in-sample training-fold scores, with a defensive fold filter (isotonic.py:68-73). K4 uses inner-validation loss only. Imputation does not apply to S^T. Hygiene note: the full label vector `F.y` is passed into `fit` (m13).
7. **Do the tests pass for the right reasons?** Not run (see above). Read statically, they test hook isolation, economy-versus-full equivalence of loss and gradients, padded-versus-unpadded equality, and peft settings. They run only on CPU, in float32, on tiny randomly initialized `*ForCausalLM` classes with synthetic layouts. That leaves the GPU path (B2), the real answer-token file (B1), real chat-template spans (M3), and the Gemma 4 conditional-generation class (M1) unexercised.

## Verified versus suspected

- Verified by reading: B1, M1 (no caller), M2, M3, M5, and m1 through m15.
- Suspected and not executed: B2, which depends on PyTorch's generator-device rule. M4 is "not located", not proven absent.
- Not verified: the pytest outcome, the Gemma 4 class that `AutoModelForCausalLM` returns, and per-checkpoint LM-head bias.

Verdict: NOT READY. The masking mechanism, the economy-path equivalence, and the leakage boundaries look correct by construction and are well tested on CPU tiny models. However, the real GPU path is expected to fail at load (B1, verified) and at adapter initialization (B2, suspected), and the design 7.12 gate (M1) and the checkpoint recipe reuse (M2) are not implemented.
